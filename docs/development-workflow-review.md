## 对 Superpowers 的处理

检查了 `using-superpowers`、`brainstorming`、`test-driven-development`、
`using-git-worktrees`、`verification-before-completion`、
`finishing-a-development-branch` 及技能编写指南。

- `brainstorming` 要求所有路径都停下等待设计批准；改为结合现有请求和授权判断，
  简单且明确的实现继续推进，影响产品方向的未决问题才询问。
- `using-superpowers` 的“1% 可能适用”会扩大无关阅读；改为只选择能帮助当前任务的技能，
  已完整读取且未变化的技能不重复加载。
- 测试与完成前验证保留证据要求；证据是否仍有效取决于代码及运行条件是否改变，
  不取决于刚切换了哪个流程步骤。文档和轻微外观改动无需强制编写机械测试。
- 工作树与分支收尾按任务风险和已有用户选择执行；不默认新建工作树，
  也不在用户已选择合并后再次给出收尾菜单。
- 委派继续由主模型判断成本与收益，并受当前工具权限约束。小型本地任务直接完成。

这些是协作偏好，写入全局和项目 `AGENTS.md` 即可；无需修改插件版本缓存或复制整套技能。
技能自身也声明用户指令优先。以后若发现某个技能仍有具体冲突，再做有针对性的修订。

## 本次核验范围

采用文件回读、变更检查和以下情景的静态推演，不重跑未变化的应用代码。
静态推演用于检查规则矛盾，不代表已证明未来所有模型都会遵循，也不是一次真实的代理行为测试。

| 情景 | 规则要求的下一步 |
| --- | --- |
| 用户已批准“增加某个设置项”，实现边界明确 | 检查相关代码后实现和验证；不重新发起设计审批 |
| 新请求涉及不同数据存储架构，迁移选择尚未确定 | 先收集资料并整理权衡，询问关键选择，继续不依赖该选择的工作 |
| 同一代码和环境刚通过测试，只是准备提交或回复 | 复用成功证据并检查最终差异；不全量重跑 |
| 快进合并后路径变化可能影响资源定位 | 检查测试覆盖与路径假设，对受影响的入口做有针对性的验证 |
| PDF.js 超时且显示渲染进程创建错误 | 收集相关日志，必要时走执行权限审批；不关闭安全机制绕过限制 |
| 工作树删除失败且还有未知文件 | 停止后续依赖操作，核对保存情况；不能直接递归删除 |
| 用户说“只合并到本地” | 完成本地合并与适当验证，不推送或打包 |

后续以真实任务观察效果，优先跟踪：不必要的用户确认次数、无新证据的重复运行次数、
从首次失败到获得有效诊断证据的轮次，以及承诺动作是否完成。不为这些指标引入后台监控。
